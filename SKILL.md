# Evolutionary Radio

> **The vision (2026-06-03):** A music radio that never stops. Every song is freshly generated by a model whose **weights** (Darwin family evolution) and **prompts** (GEPA prompt evolution) are continuously improving in the background. One prompt from the user → infinite playback.

This skill is the **master orchestrator** for that vision. It owns the queue, the playback loop, the generation loop, the GEPA prompt evolution, and the Darwin weight evolution. It is the **single place** to look when you want to start, stop, evolve, or hot-swap the radio.

## When to use this skill

Activate when the user says any of:
- "Evolutionary Radio" / "OmniStep Radio" (the official names; NOT "jam" or "jamming")
- "infinite radio" / "infinite generative radio" (describes the same idea)
- "queue up music that evolves" / "music that gets better over time"
- "I want to put a prompt in and have it just keep playing"
- Wants to add a new DiT voice to the radio (e.g., "swap ACE-Step for MusicGen")
- Wants to run GEPA on the radio's prompt template
- Wants to run Darwin CMA-ES on the radio's voice weights
- "Wire up the radio" / "Build the radio"

Do NOT activate for:
- One-off music generation (use the `songwriting-and-ai-music` skill or `heartmula` skill)
- Static-library playback (use `spotify` skill or the `herm-tui-radio` bottom-bar)
- Music editing of an existing track (see [[music-editing-pipeline]] — TBD, planned)

## Architecture: four concurrent loops

The system runs four loops in parallel. None block the others. The playback loop has hard real-time constraints; the rest run in the background.

```
┌────────────────────────────────────────────────────────────────────────┐
│  Evolutionary Radio (single Python process, asyncio)                   │
│                                                                        │
│  ┌─ Loop 1: PLAYBACK ─────────────────────────────────────────────┐    │
│  │  asyncio.Queue → mpv (--input-ipc-server=...) → EOF/skip → ... │    │
│  │  HARD real-time: must dequeue < track length                  │    │
│  └────────────────────────────────────────────────────────────────┘    │
│  ┌─ Loop 2: QUEUE FILL ───────────────────────────────────────────┐    │
│  │  if qsize < 5: POST /release_task to ACE-Step → poll result   │    │
│  │  → put track on queue. Sleep 5s, check again.                 │    │
│  └────────────────────────────────────────────────────────────────┘    │
│  ┌─ Loop 3: GEPA PROMPT EVOLUTION (slow) ──────────────────────────┐    │
│  │  read skip_log + CLAP scores → GEPA reflect → new prompt      │    │
│  │  cadence: every 50 generations OR 1 hour of listening        │    │
│  └────────────────────────────────────────────────────────────────┘    │
│  ┌─ Loop 4: DARWIN WEIGHT EVOLUTION (slowest) ─────────────────────┐    │
│  │  CMA-ES on ACE-Step × Stable Audio 2 → FAD/CLAP → update     │    │
│  │  cadence: nightly or weekend                                   │    │
│  └────────────────────────────────────────────────────────────────┘    │
└────────────────────────────────────────────────────────────────────────┘
```

## The "magic number" — generation vs. playback latency

| Voice model | Gen latency (60s song) | VRAM | Radio-friendly? |
|---|---|---|---|
| **ACE-Step v1.5 SFT 2B** ← default | ~7-10s on RTX 3090 | ~8-12GB | Yes — fill rate much greater than playback rate |
| ACE-Step v1.5 XL 4B DiT | ~20-30s on RTX 3090 | ~20-24GB | Tight — still keeps queue if target = 5 tracks |
| MusicGen-stereo-large 3.3B | ~30-60s | ~10GB | Slow but viable |
| Stable Audio 2 | ~10-20s | ~6GB | Yes (also a Darwin merge partner) |

**Rule of thumb:** voice gen latency < (queue_target × track_length) / target_tracks_played_per_minute. With 5-track queue and 60s tracks, the budget is 5×60 = 300s of generation per 60s of playback. Any voice that generates a 60s track in <300s keeps the queue full.

## Components

### Brain: OmniStep 6B (port :11450)
The Darwin-merged text LLM. Generates the prompt template that gets sent to ACE-Step. Has the music-domain knowledge baked in via the merge with ACE-Step's text body. See [[omnistep-6b]].

### Voice: ACE-Step v1.5 SFT 2B (port :7860)
The DiT decoder that turns text prompts into audio. Default voice. See [[ace-step-v15-sft-2b]].

### Player: mpv with Unix socket IPC
Uses `--input-ipc-server=/tmp/hermes-mpv-<uuid>` so we can send `{"command": ["loadfile", ...]}` and `{"command": ["set_property", "pause", true]}` over a Unix socket. The Ink TUI's `tui_gateway/server.py` already has the working pattern (see `herm-tui-radio` skill pitfall list).

### Queue: in-process asyncio.Queue
Bounded at 5 tracks. `asyncio.Queue(maxsize=5)`. Producer = Loop 2. Consumer = Loop 1.

### Trainer (Loop 3): GEPA prompt evolution
Arxiv 2507.19457 (Agrawal et al., 2025) — *Reflective Prompt Evolution Can Outperform Reinforcement Learning*. Population of N prompt templates, natural-language reflection, Pareto-front maintenance. We use it to evolve the **prompt sent to ACE-Step**, not the model. See [[gepa-prompt-evolution]].

### Evolver (Loop 4): Darwin weight evolution
The CMA-ES loop from the [[darwin-family-paper]]. Operates on the **DiT weights** of the voice. Fitness = FAD + CLAP score. See [[generative-darwin-evolution]] and the `evolutionary-model-merging` skill.

|---|---|
| `radio start --vibe="chill lofi"` | Begin all 4 loops; pass vibe to OmniStep prompt template |
| `radio start --prompt="aggressive metal, 140bpm"` | Use literal prompt instead of vibe |
| `radio stop` | Stop playback, drain queue, kill ACE-Step process |
| `radio skip` | Skip current track, dequeue next |

| `radio resume` | Resume from pause |
| `radio status` | Print: queue depth, last 5 tracks, last gen latency, OmniStep prompt template, GEPA gen count, Darwin gen count |

## Key design decisions

1. **OmniStep is the brain, not a music model.** It generates the *prompt* sent to ACE-Step. This is what makes the system "evolutionary" in the prompt dimension (GEPA) and weight dimension (Darwin) simultaneously.
2. **ACE-Step 2B is the default voice, not 4B XL.** Speed matters more than quality for an infinite radio. The 2B's 7-10s generation is what makes the queue race winnable. 4B XL is for HQ mode.
3. **The queue is the only hard constraint.** 3-5 tracks ahead means the user can skip 5 times in a row and the music still keeps flowing. Below 3, start to feel starvation. Below 1, dead air.
4. **Skip rate is the primary fitness signal.** Not CLAP, not FAD. The user is the ground truth. GEPA evolves the prompt template to reduce skip rate; Darwin evolves the voice weights to be sonically better.
5. **GEPA + Darwin are independent loops.** GEPA is fast (LLM API calls, minutes). Darwin is slow (full merge, hours). They don't block each other. GEPA can run on the current voice; Darwin replaces the voice when ready.

## Pitfalls (compiled from this session)

### 1. mpv IPC socket cleanup
mpv's `--input-ipc-server` creates a Unix socket at the given path. This socket is **left behind** after mpv exits. The launcher's `_music_stop_proc` should also `os.unlink(socket_path)`. Use UUID-prefixed paths (`/tmp/hermes-mpv-<uuid>`) to avoid collisions across restarts.

### 2. ACE-Step VRAM footprint
~8-12GB on RTX 3090. Don't launch ACE-Step if the brain (OmniStep 5GB) + something else is already on GPU. Always check `nvidia-smi` first. **Kill ACE-Step when radio is not active:** `pkill -f acestep.api_server`.

### 3. mpv cannot use socat
mpv IPC is a Unix socket. Don't try to shell-pipe through socat (often not installed). Use Python's `socket` module directly — see `tui_gateway/server.py` for the working pattern.

### 4. OmniStep might be running on :11450, but check
The current OmniStep 6B is on :11450 (per the OmniSenter architecture wiki). Verify before starting the radio: `curl http://localhost:11450/v1/models`. If it's not there, the brain needs to be launched first.

### 5. ACE-Step API status codes
- `status: 0` = pending
- `status: 1` = complete (audio in result.audio as bytes)
- `status: -1` = failed (retry with a different prompt; don't infinite-loop on the same prompt)

### 6. Queue starvation under sustained skip
If the user skips 10 times in a row, the queue can drain in ~1-2 minutes (10 × 6-12s per skip). Loop 2 has a 5s sleep — adjust to 1s during heavy skip periods, or check `qsize()` more aggressively.

### 7. GEPA reflection quality
The reflection prompt matters more than the optimizer. A bad reflection ("how could this be better?") produces bad mutations. Use: *"This prompt produced a track the user skipped after N seconds. Given the user-skip rate, what tag combination in the prompt would have produced a more compelling track? Be specific."*

### 8. Darwin evals are NOT real-time
A full FAD + CLAP eval on 100 FMA clips takes ~5-10 minutes per candidate. With 20 candidates per generation × 20 generations, that's **67-200 hours of GPU time**. Run Darwin overnight, not interactively.

### 9. mpv `--no-video` and `--no-terminal`
Always pass `--no-video` (we're audio-only) and `--no-terminal` (don't print status to stdout, the radio process owns stdout). Also `--quiet` for less stderr noise.

### 10. `signal.SIGTERM` propagation
The radio process should propagate SIGTERM to mpv, ACE-Step subprocess, and the GEPA loop. Use `asyncio.create_subprocess_exec` for mpv and ACE-Step, and propagate signals to the task group.
